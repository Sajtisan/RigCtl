# Project Plan — RigCtl

## Overview

**RigCtl** is a lightweight, modular Linux hardware control system designed primarily for my own Omarchy-based desktop setup.

The project will provide three independently installable modules:

- **Mouse Controller** — Razer Viper V3 HyperSpeed
- **Keyboard Controller** — Ajazz AK820 MAX
- **Fan Controller** — fan profiles and custom fan curves

The main goals of the project are:

- minimal system resource usage;
- modular architecture;
- direct Linux hardware integration;
- reverse engineering unsupported hardware;
- CLI-first development;
- a lightweight browser-based GUI.

The CLI implementations will be developed first. The browser interface will later act as a frontend for the already existing functionality.

---

## Subject to Change

This project plan is subject to change as development progresses. The scope, planned features, architecture, module design, and development phases may be revised based on hardware limitations, reverse-engineering findings, testing, and changing priorities.

## Architecture

```text
                             Browser UI
                                  │
                              Local API
                                  │
                               RigCtl
                                  │
            ┌─────────────────────┼─────────────────────┐
            │                     │                     │
            ▼                     ▼                     ▼
          Mouse               Keyboard                Fans
         Module                Module                Module
            │                     │                     │
        OpenRazer              USB/HID          Linux fan control
```

The hardware-specific logic will be separated from both the CLI and the browser interface.

Each hardware controller will be implemented as an independent module so that its implementation can later be extracted or contributed to an existing open-source project.

## Module System

RigCtl will use optional modules.

During installation, the user can choose which components should be installed.

Example:

- [x] RigCtl Core
- [x] Mouse Controller
- [x] Keyboard Controller
- [ ] Fan Controller

Modules that are not enabled will not be downloaded or installed.

If a module is enabled later, its required files and dependencies will be installed separately.

If a module is disabled, it will be marked for removal and uninstalled during the next system restart.

This keeps the installation minimal and prevents unused components from consuming system resources.

## Mouse Controller

The mouse module will control my Razer Viper V3 HyperSpeed directly through OpenRazer without requiring Polychromatic.

Planned functionality:

- device detection;
- DPI configuration;
- polling rate configuration;
- battery information;
- supported device settings;
- communication with the OpenRazer backend.

Example CLI commands:

```bash
rigctl mouse status
rigctl mouse dpi 800
rigctl mouse polling-rate 1000
```

The OpenRazer-specific implementation will remain isolated from the rest of RigCtl.

## Keyboard Controller

The keyboard module will provide Linux configuration support for my Ajazz AK820 MAX.

Since there is no complete Linux configuration software available for the keyboard, a significant part of the project will involve reverse engineering its configuration protocol.

The investigation may include:

- USB/HID traffic capture;
- comparison of commands generated by the official software;
- HID report analysis;
- protocol documentation;
- binary analysis of the official application if necessary.

Planned functionality:

- reading the current keyboard configuration;
- key remapping;
- Fn-layer configuration;
- macros;
- polling rate;
- keyboard profiles;
- other device-specific settings where possible.

Example CLI commands:

```bash
rigctl keyboard status
rigctl keyboard keymap get
rigctl keyboard remap capslock escape
rigctl keyboard profile apply gaming
```

The reverse-engineered protocol will be implemented separately from the CLI:

```text
 Ajazz Protocol
       │
       ▼
Keyboard Backend
       │
       ├── CLI
       │
       └── RigCtl API
```

This separation should make it possible to reuse the protocol implementation in another Linux project later.

## Fan Controller

The fan module will focus specifically on fan profiles and fan curves.

A profile will contain one or more temperature-to-fan-speed mappings.

Example fan curve:

```text
30°C → 20%
45°C → 30%
60°C → 50%
75°C → 75%
85°C → 100%
```

The CLI will use a compact representation:

```bash
rigctl fans profile create silent \
  --curve "30:20,45:30,60:50,75:75,85:100"
```

The format will be: `temperature:fan-speed`

Profiles can then be applied using commands such as:

```bash
rigctl fans profile apply silent
rigctl fans profile apply balanced
rigctl fans profile apply performance
```

The browser interface will provide a graphical fan-curve editor, while the CLI and GUI will use the same underlying profile format.

The module will validate curves before applying them, for example:

- temperatures must be ordered correctly;
- fan speed must remain within valid limits;
- invalid or incomplete curves must not be applied.

## CLI

All important functionality must be usable without the browser interface.

The CLI is therefore the first interface that will be implemented.

Example:

```bash
rigctl mouse dpi 800
rigctl keyboard remap capslock escape
rigctl fans profile apply silent
```

This ensures that the hardware logic remains independent from the graphical interface.

## Browser Interface

After the CLI modules are functional, RigCtl will provide a browser-based user interface served locally.

Example: `http://localhost:<port>`

The browser interface will provide graphical configuration for the three modules.

### Mouse

- DPI configuration;
- polling rate;
- battery information.

### Keyboard

- visual keymap;
- key remapping;
- Fn-layer editing;
- macro configuration;
- keyboard profiles.

### Fans

- profile management;
- graphical fan-curve editor.

The frontend should remain a thin layer over the existing backend instead of containing hardware-specific logic.

## Resource Usage

Low resource usage is one of the main design goals.

RigCtl should avoid unnecessary background processes.

The planned principles are:

- no permanently running desktop GUI;
- browser UI only when required;
- unused modules are not installed;
- installed modules should not automatically require separate background processes;
- hardware operations should run only when necessary;
- only functionality that requires continuous monitoring should remain active.

The browser frontend itself does not need a separate Electron-style runtime.

## Engineering Challenges

### 1. Ajazz AK820 MAX Reverse Engineering

The largest technical challenge will be understanding the undocumented keyboard configuration protocol.

The expected workflow is:

```text
   Official software
           │
           ▼
USB/HID traffic capture
           │
           ▼
   Packet comparison
           │
           ▼
  Protocol hypothesis
           │
           ▼
 Linux implementation
```

The goal is to document enough of the protocol to configure the important keyboard features directly from Linux.

### 2. Different Linux Hardware Interfaces

Each module communicates with hardware differently:

```text
Mouse       → OpenRazer / D-Bus
Keyboard    → USB / HID
Fans        → Linux hardware interfaces
```

The application must keep these implementations independent while exposing them through a consistent interface.

### 3. Modular Installation

The program must manage:

- installed modules;
- enabled modules;
- modules available for download;
- dependencies;
- modules scheduled for removal.

### 4. Low Resource Usage

The architecture must avoid unnecessary long-running processes while still providing convenient access to hardware controls.

### 5. Fan Curve Validation

User-defined fan curves must be represented, stored and validated consistently between the CLI and graphical interface.

## Expected Result

By the end of the project:

- the Razer mouse should be configurable directly through RigCtl;
- the most important Ajazz AK820 MAX settings should be controllable from Linux;
- key remapping should work without the official Windows application;
- custom fan profiles and fan curves should be configurable;
- all three modules should be usable from the CLI;
- a browser-based interface should expose the implemented functionality;
- modules should be independently installable and removable;
- unused functionality should have minimal or zero runtime cost;
- hardware-specific implementations should be sufficiently independent to allow later reuse or contribution to existing open-source projects.

The project will be developed in a public GitHub repository with regular, traceable commits.
